# FIX_DESIGN — v4 pipeline (design only; no code, v3 untouched)

Revision 2. Companion to `THREAT_MODEL.md` (hypotheses) and `RESULTS_BINDING.md`
(2026-11-03 measurements: every hypothesis confirmed; wrong-accepts A4/A5/A6/A7).
Designs the **minimum** v4 that closes the measured binding gaps. Nothing here is
implemented; v3 circuit/artifacts/pins stay frozen.

**Rev-2 changes vs rev-1:**
- Change 5 (`proof_pub_sha256`) is **REMOVED** — it contradicted Change 4: the
  record is signed at enrollment, and hashing `session_nonce` into it would
  reject every fresh-nonce proof forever. Record↔proof binding is achieved
  instead by `metadata_commitment` + `file_sha256` + `vkey_sha256` (argument in
  Change 1/§"Record↔proof binding").
- The five rule constants are now **verifier-chosen public inputs** (Change 1b).
- The trust story is corrected: the **issuer sees the plaintext metadata** at
  enrollment (it stands in for a trusted capture device), checks it, generates
  the salt, computes C, signs C, and privately hands (metadata, salt) to the
  holder. ZK provides *verifier-side* privacy and *post-enrollment* policy
  choice — not secrecy from the issuer.

**Design principle carried over from v3:** fail-closed, pinned trust, explicit
loud overrides, honest labeling — every claim is scoped to what cryptography
binds. Content-identity attacks (A2/A3/A8) remain open (§Predicted verdicts).

## The five changes

### Change 1 — Metadata commitment C (closes A4)

- **Circuit** (`circuits/provenance_v4.circom`, new file):
  - **Private** signals: the five v3 metadata inputs + `salt` (random field
    element generated by the ISSUER at enrollment, handed privately to the
    holder, never stored in any record, never revealed).
  - **Public output**: `C = Poseidon(device_id, timestamp, sensor_score,
    gps_lat, gps_long, salt)` (circomlib Poseidon, nInputs=6, BN-254).
  - All v3 constraint logic unchanged (limb range checks, rules — now
    parameterized per Change 1b — and `valid_claim === valid`).
- **Why the salt:** the rule ranges are small (≈6×10^10 combinations), so an
  unsalted C would be brute-forcible from the record alone. With the salt, C
  reveals nothing to verifiers and cannot be re-targeted: a proof with forged
  metadata `m'` requires `Poseidon(m', salt') = C_signed`, a preimage on an
  unknown, non-invertible permutation.
- **Trust placement (corrected):** the ISSUER — standing in for a trusted
  capture device — sees the plaintext metadata at enrollment, checks it is
  well-formed against its own reference policy, generates the random salt,
  computes C with the same Poseidon the circuit uses (via witness generation:
  `snarkjs wtns calculate` on the enrollment input — deterministic, no proof
  needed), **signs C into the record**, and privately hands `(metadata, salt)`
  to the holder. **Metadata truth rests on the issuer/device, not on ZK.**
- **Holder:** from enrollment onward, the holder generates proofs for *any*
  verifier's policy and nonce, revealing neither the metadata nor the salt —
  publicly, only the rule-outputs and C are visible.

### Change 1b — Verifier-chosen rules (public policy inputs; closes the fixed-policy limitation)

- **Circuit:** the five hard-coded v3 constants become **public inputs**:
  - `allowed_device_0, allowed_device_1, allowed_device_2` — fixed-size 3-slot
    allow-list (repetition encodes smaller lists; a verifier allowing one
    device sets all three slots to it).
  - `timestamp_min, timestamp_max`, `gps_lat_min, gps_lat_max`,
    `gps_long_min, gps_long_max` — range bounds.
  - `sensor_min` — a single ≥ bound.
  - Rule logic: same comparators as v3, but `in[0]`/`in[1]` both signals.
- **Verifier policy:** `verify_media_v4.js` takes `--policy-file <policy.json>`
  with fields `{device_ids:[a,b,c], timestamp_range:[t0,t1], gps_lat_range:[x0,x1],
  gps_long_range:[y0,y1], sensor_min:s}` and **checks the proof's public policy
  signals equal its policy exactly** (all ten, in order). Because Groth16 binds
  public inputs via `vk_IC`, a proof computed under a weaker policy cannot be
  presented to a stricter verifier: the policy fields are part of the proven
  statement, and the verifier-side equality check names any mismatch.
- **Bit-width limitation (stated):** bounds must fit the v3 comparator widths
  (`timestamp ≤ 2^31−1; sensor ≤ 255; lat ≤ 2^19; lon ≤ 2^20`); a policy whose
  `t0 > t1` (or otherwise empty range) makes the circuit unsatisfiable — an
  honest proof simply fails, fail-closed. These widths could be widened in a
  future circuit revision; not now (minimal change).
  **Range-soundness audit (2026-11-04, Part A):** no operand needs its own
  `Num2Bits` -- each comparator internally constrains the difference
  `in[0] + 2^n - in[1]` to [0, 2^(n+1)) via `Num2Bits(n+1)`, exact over the
  field (p >> 2^(n+1) forbids mod-p aliasing), so any operand outside its
  difference window fails witness generation (verified by negative tests:
  p-1 metadata, 2^31+k timestamps, attacker bounds >= 2^n all fail to prove).
  The only crypto-verifiable "escape" is an attacker-chosen self-consistent
  policy (e.g. timestamp = bound = 2^100), which the verifier's
  policy-equality check rejects -- therefore the v4 policy loader (step 4)
  must reject policy values that exceed the comparator bit-widths
  (t <= 2^31-1, sensor <= 255, lat <= 2^19, lon <= 2^20) for clear errors
  rather than relying on fail-closed witness failures.

### Change 2 — Detector attestation at enrollment (closes A5)

- The **issuer runs AASIST-L itself** at enrollment (fresh detection — not a
  copy of any CLI manifest; measured A5 showed `demo_result.json` is forgerable
  and read by nobody).
- **Record fields (new, signed):** `det_checkpoint_sha256`, `det_threshold`
  (full decimal string of the fixed policy value), `det_score_decimals6`
  (raw score at exactly 6 dp so the canonical string is
  formatter-independent), `det_decision`.
- **Verifier behavior:** after the signature verifies, prints the tuple
  verbatim. The signed record becomes the only record of detection truth; the
  manifest remains an unconsumed convenience artifact.
- **Scoping:** this attests *what the issuer measured at enrollment* — not that
  the speech is human.

### Change 3 — Enrollment policy (closes A7; inherits detector errors by design)

- **Chosen: issuer refuses to sign on a spoof decision; `flagged=true` only via
  an explicit loud override.**
  - `issue_capture_record_v4.js`: if the issuer's own detection says
    `spoof` → exit 1, `refusing: enrollment decision = spoof` (no record).
  - `--allow-spoof-enrollment` issues the record with `flagged=true`
    (auditable compromise; same pattern as the existing pin overrides).
  - Honest-genuine files the detector wrongly spoofs (MEASURED: 1/10 sampled
    genuine, `LA_E_8374049`) are refused — accepted availability loss.
- **Verifier:** `flagged == true` → REJECT unless `--allow-flagged` (loud).
- **Stated clearly:** the pipeline's authenticity claim equals *"AASIST-L said
  bonafide at enrollment"*. All detector error rates (full-eval EER 0.9909%)
  become system error rates: ~1% of spoofs enroll; ~1% of genuine files are
  refused. **The threshold was tuned on the eval set** (RESULTS_BINDING.md §6:
  full-eval EER point 1.7635419737) — it is not a validated deployment
  operating point, and no new threshold tuning is in scope here.

### Change 4 — Context (closes cross-time A6; partial by design)

- **Record field (new, signed):** `expires_at_utc` (ISO-8601 UTC, same
  convention as `issued_at_utc`), set via `--expires-hours N` (default 24).
- **Freshness check:** `issued_at_utc <= now <= expires_at_utc` at verification
  wall-clock; expired → distinct REJECT reason.
- **Optional verifier nonce bound into the PROOF, not the record** — forced by
  signing order: the record is signed at enrollment, before a session nonce
  exists, so a record-carried nonce is dead on arrival (this is also why
  rev-1's Change 5 was contradictory and is removed). Design:
  - Circuit public input `session_nonce` (field element; `0` when no session
    context). Groth16 binds public inputs via `vk_IC` → **zero** constraint
    cost.
  - Verifier may pass `--expect-nonce N`; the proof's public nonce must equal
    N. A replayed stale proof carries the old nonce → fails a fresh session;
    re-proofing requires the private salt (Change 1's preimage wall).
- **Residual (stated):** replay *within* the expiry window without an expected
  nonce remains possible; expiry+freshness shrink that window, the nonce
  eliminates it when used.

### Record↔proof binding without Change 5 (replaces the removed `proof_pub_sha256`)

The record and the proof are bound **both ways** by three record fields:

- **record → proof:** `metadata_commitment` — the presented proof's public `C`
  must equal it (a proof under different metadata/salt has a different C, and
  finding a second preimage is infeasible); `vkey_sha256` — fixes the exact
  verification key, hence the constraint system, the `vk_IC` encoding, and the
  public-signal layout the record was issued against.
- **proof → record:** `file_sha256` — verify_media_v4 recomputes the SHA-256
  of the presented file and matches BOTH the proof's `media_hash_hi/lo` limbs
  AND the record's `file_sha256` (unchanged v3 closure, now checked on both
  sides).

A mismatched pair (record of X + proof of Y) must therefore fail on `C`
(different commitment) or on `file_sha256` (different bytes) — the two fields
are independent anchors, and the vkey pin prevents re-keyed substitutions.

Fail-closed; distinct reasons; exit 0 ACCEPT / 1 REJECT / 2 usage.
Signal-count note (corrects rev-2 text): snarkjs emits **outputs first**, so
`public.json` has **16** entries — `[valid, C, media_hash_hi, media_hash_lo,
valid_claim, session_nonce, allowed_device_0..2, timestamp_min/timestamp_max,
gps_lat_min/gps_lat_max, gps_long_min/gps_long_max, sensor_min]` — 2 outputs +
14 declared public inputs, in declaration order.

1. **Part A′** — `scripts/verify_media_v4.js` spawned independently on its own
   pinned v4 vkey, checking: files parse; vkey pin; public shape = **14
   decimal strings** in order `[valid, media_hash_hi, media_hash_lo,
   valid_claim, C, session_nonce, allowed_device_0/1/2, timestamp_min,
   timestamp_max, gps_lat_min, gps_lat_max, gps_long_min, gps_long_max,
   sensor_min]`; **policy equality** with the verifier's `--policy-file`;
   `valid == valid_claim == "1"`; SHA-256 recompute of the file == limbs; real
   `snarkjs.groth16.verify` (accept only literal `true`).
2. **`metadata_commitment` equality:** proof's public `C` == record's C —
   *before* any other record interpretation, so a C-mismatch fails with a
   nameable reason (Change 1).
3. **Record structural checks:** `record_version == 2`, `record_type`, all
   required fields present (attestation four, `metadata_commitment`,
   `expires_at_utc`, `flagged`, standing fields).
4. **Issuer key:** pinned public key SHA-256 (unchanged pin);
   `--trusted-pubkey` requires explicit `--expect-pubkey-sha256`, as in v3.
5. **Canonical form + Ed25519 verify** under the pinned key (unchanged
   mechanics, revised field list — **no** `proof_pub_sha256`).
6. **Freshness:** `issued_at_utc <= now <= expires_at_utc` (Change 4).
7. **Enrollment policy:** `flagged == true` → REJECT absent explicit
   `--allow-flagged`; attestation tuple printed with the verdict either way
   (Change 3).
8. **Session nonce (optional):** with `--expect-nonce N`, public nonce must
   equal N; without it, the public nonce must be `0` (Change 4).
9. **Final decision:** `RESULT : FULL-VERIFY ACCEPT` / `REJECT — <reason>`,
   with the standing label: proof + file binding + enrollment-time
   issuer-attested metadata (committed value C; plaintext hidden from the
   verifier) + enrollment-time detector verdict — not "authentic audio", not
   content identity.

## Constraint budget & trusted setup (updated for public bounds)

- v3: **458** constraints, decomposed ≈ 2×`Num2Bits(128)` (≈258) + comparators
  and claim chain (≈200).
- **Constant→public-signal substitution is free in circomlib:** `IsEqual`,
  `GreaterEqThan(n)`, `LessEqThan(n)` are already two-SIGNAL templates — v3 fed
  constants into the same signal slots. The comparator count and per-comparator
  cost are therefore unchanged; only the operands become verifier-visible
  signals. New signals (`salt`, `session_nonce`, 10 policy publics) and the `C`
  output wire add no constraint-cost beyond the hash itself (public inputs are
  bound by `vk_IC`, not by constraints).
- **`Poseidon(6)` is the only real addition: ≈ 400–700 constraints** (full +
  partial round permutations at width 6; exact figure only from the compiled
  `.r1cs` — the build step must assert `≤ 4096`).
- **Estimated v4 total: ≈ 900–1,150 constraints ≪ 4,096** (unchanged from
  rev-1's estimate; the policy change does not move it).
- **New trusted setup: YES — phase 2 only.** Recompile (circom 2.2.3), fresh
  zero-contribution `groth16 setup`, new `circuit_v4.zkey` +
  `verification_key_v4.json`, new pins in the v4 verifier.
  **`pot12_final.ptau` is REUSED** (phase-1 is constraint-count-scoped and
  still valid below 4,096). v3 artifacts and pins stay frozen; all v4 code in
  new `_v4` filenames so the v3 pipeline remains runnable.

## What the ZK proof provides that S2 (hash + Ed25519 only) cannot

S2's fundamental choice: the issuer signs **plaintext metadata** or a fixed
**"rules passed" bit**. Both fail in a way the v4 circuit does not:

- **Plaintext signing** forces the issuer to hand verifiable metadata to every
  verifier — verification privacy is gone, and the metadata leaks to everyone
  who ever receives the record.
- **A fixed rules-passed bit** freezes the policy at enrollment: the bit says
  "passed *some* rules, under the enroller's policy, at enrollment time".

**Concrete example — one record, two verifiers:** after enrollment, verifier
V1 requires `device = 1024` and window `[1780290000, 1780300000]`; verifier V2
(holding the same record) requires any of `{1024, 2048}` and a wider window
`[1780278000, 1780867200]`. Under S2-with-bit, both V1 and V2 must take the
enroller's word — the bit is opaque, and neither can tighten, loosen, or
parameterize the rules, because the rules were chosen (and hidden) *before*
either verifier existed. Under S2-with-plaintext, both learn the exact device,
times, and GPS coordinates — V1 and V2 see everything, and whatever logs,
caches, or intermediaries carry the record leak it too. In v4, **V1 and V2
each pass their own policy publics**, and the same holder proves acceptance —
or rejection — of *their specific* policy with no disclosure of the metadata
or salt: V1 can even shrink its window retroactively to a range the enrollment
never anticipated. That last capability — **proof over an arbitrary, verifier-
chosen policy, for data committed before the policy existed, with the
committed values never revealed** — is the concrete thing S2 cannot provide.
Caveat (stated): if a deployment were willing to reveal metadata, an issuer
signature over rules-checked plaintext would subsume the entire circuit; the
proof is load-bearing exactly when verifier-side privacy (or policy
flexibility after enrollment) is load-bearing.

### Policy-oracle leakage (new, rev-2)

A verifier that can request many proofs **narrows its window policy between
queries** and binary-searches the hidden metadata through the accept/reject
signal: ~30 timestamp queries pinpoint an enrolled timestamp at 1 s resolution
(2 ceil(log2(588,201)) ≈ 20 for the v3 range; ~30 if the attacker probes a
365-day range at 1 s); symmetric attacks apply to gps bounds and `sensor_min`
(~7 queries for a 0–255 score, ~10 per GPS axis). The accept/reject bit is
itself an oracle — no circuit change can prevent it while verdicts are binary
and unlimited queries are allowed.

**Mitigation, layer 1 (width floors — MEASURED DEFECTIVE, superseded by the grid):**
the holder initially refused policies narrower than configured minimums
(timestamp ≥ 3,600 s, gps ≥ 100 = 0.01°). The 2026-11-05 leakage measurement
(eval/leakage_sim.py, eval/leakage_sim_results.json) showed the width floor is
not merely insufficient but DEFEATED: the verifier anchors the probe window's
RIGHT edge far beyond its candidate interval (any policy [t, HI] with HI at the
range end keeps the width ≥ floor for arbitrary t), making accept monotone in
t — plain bisection (~18 queries) recovers the timestamp to 1 s EXACTLY, the
same as no guard at all (measured: a_no_guard 18 queries / 1 s;
b_min_width 18 queries / 1 s; gps identical). A width floor constrains the
WINDOW, but the verifier's information comes from the window's POSITION,
which remains free. Layer 1 is kept only as a cheap sanity floor.

**Mitigation, layer 2 (grid alignment — built 2026-11-04, THE effective guard,
measured 2026-11-05):** every policy bound must lie on a per-field grid:
`timestamp_min ≡ 0 mod G_t` and `(timestamp_max + 1) ≡ 0 mod G_t` (G_t = 3600,
epoch-anchored — note an aligned window's width ≡ 3599 mod 3600), and lat/long
bounds ≡ 0 mod G_g (G_g = 100). Misaligned → refusal `policy bounds not
grid-aligned (<bound>)`, no proof. Measured effect: probe positions are
quantized AND the right-edge-extension trick dies (the extended right edge must
align too, and the grid's granularity is what the candidates collapse to):
bisection over GRID-ALIGNED probe positions recovers only a CELL (measured:
8 queries -> 3,600 s one-cell precision, 7.35 bits for the timestamp; 4 queries
-> 100 units, 3.32 bits for gps_lat; vs EXACT for both under no guard or
width-floor-only). Built into the holder with tests (sliding-window refused;
aligned-window accepted).

**Stated residual:** the verifier still learns WHICH GRID CELL holds the value
(≤ log2(cells) bits over the whole policy), and every refusal is itself a 1-bit
answer — rate-limiting remains necessary. Optional per-verifier query budget:
holder config `enforce_query_budget` (default off) counts consecutive
width/grid refusals in `budget_file` and refuses past `budget_max`
(default 100). Holder-side device allow-list: a single-distinct-device policy
is allowed by default (`refuse_single_device: false`) — residual: every ACCEPT
confirms "enrolled with device X", which the verifier already knew from
choosing X; the channel is limited to confirming enrolled-vs-not and is closed
only via the config opt-in.

**Planned measurement** (extends §Planned experiment): with the limit enabled,
queries needed to pin each field to 1 s / 0.01° / 1 point must exceed the
config floor (report exact counts with and without the limit, e.g. timestamp:
~20 queries unhindered vs 0 successful narrows below the 3600 s floor).

**Holder-side policy guard (step 6):** minimum range widths are enforced by the
holder (holder config: timestamp ≥ 3,600 s, gps_lat ≥ 100, gps_long ≥ 100; all
defaults). Device allow-list: the holder allows a single-distinct-device
allow-list by DEFAULT (`refuse_single_device: false`); the residual leak, stated:
a verifier choosing a one-device allow-list makes every ACCEPT reveal the
holder's device_id — the verifier can only confirm "device ∈ {X}", which it
already knew from choosing X, so the leak is limited to distinguishing
"enrolled with device X" vs "not provable" — refused entirely only when the
holder config sets `refuse_single_device: true`.

retuning, revocation, ceremony-grade setup, comparator bit-width changes —
no features beyond the five changes.

## Limitations (carried and rev-2 additions)

- The detector threshold was tuned on the eval set (full-eval EER point) — not
  a validated deployment operating point; no retuning in scope.
- The detector gate inherits its ~1% error rate in both directions (measured:
  enrolled-spoof acceptance risk ≈ FPR; honest-file refusal ≈ FNR, incl. the
  measured `LA_E_8374049` false-reject).
- A2/A3 (content identity on the enrollment path) and A8 (physical laundering)
  remain open; the simulated issuer remains the standing trust assumption.
- Policy bounds must fit the v3 comparator bit-widths (t ≤ 2^31−1, sensor ≤
  255, lat ≤ 2^19, lon ≤ 2^20); empty/contradictory ranges fail closed.
