### 1.3 SHA-256 hashing

- **`scripts/hash_limbs.js`** — `node scripts/hash_limbs.js <file> [--json out]`.
  Streams exact file bytes → SHA-256 hex → **two 128-bit decimal limbs**
  (`media_hash_hi` = first 16 bytes big-endian, `media_hash_lo` = last 16
  bytes), BigInt only (never through JS Number). Exports `sha256File`,
  `limbsFromDigest` (used by provers and verifier alike).
- **`scripts/hash_media.js`** — `npm run hash-media`; prints a file's SHA-256
  only (v1-era; the circuit work uses hash_limbs.js).

### 1.5 Ed25519 issuer (simulated trusted issuer)

- **Code:** `scripts/issue_capture_record.js` — `node scripts/issue_capture_record.js <audio> <record.json> --issuer-key <pem>` (or env `CAPTURE_ISSUER_KEY`).
- **Signs** a versioned record over a canonical `\n`-joined UTF-8 string of
  fixed-order fields: `record_version(1)`, `record_type(simulated_capture_record)`,
  `file_sha256`, `vkey_sha256` (digest of the trusted v3 vkey, so a record can't
  be replayed across a re-key), `issued_at_utc`, `issuer_label`. Signature:
  Node `crypto.sign(null, …)` with **standard Ed25519**.
- **Keys:** private pkcs8 + public spki PEM at `<HOME>\zkp-demo-issuer-keys\`
  (outside the repo, present on disk; in-repo key paths are refused; key
  material never printed). Public key SHA-256 pin hard-coded in
  `verify_fully.js`: `38fefd71…ddf645`.
- **Outputs:** `<record.json>` with the six signed fields +
  `signature_algorithm: "ed25519"`, `canonical_sha256`, `signature` (base64).
  Refuses to overwrite an existing record.

## 2. The ZK circuit in plain English (`circuits/provenance_v3.circom`)

**Private inputs (witness, never revealed):**
`device_id`, `timestamp`, `sensor_score`, `gps_lat`, `gps_long` (absolute value of longitude)

**Public inputs:**
`media_hash_hi`, `media_hash_lo` (the file SHA-256 split into two 128-bit
limbs) and `valid_claim` (prover's assertion that all five rules hold).
Public output: `valid`.

**Constraints (458 total):**
1. Each 128-bit limb is bit-decomposed with `Num2Bits(128)` — range-constrains
   the public inputs to exactly 128 bits so the limb pair decodes to a UNIQUE
   256-bit digest (no field-modulo aliasing).
2. `device_id ∈ {1024, 2048, 4096}` (three `IsEqual` OR'ed).
3. `timestamp ∈ [1780278000, 1780867200]` (pair of comparators AND'ed).
4. `sensor_score ≥ 70`.
5. `gps_lat ∈ [407400, 408400]` (scaled by 10,000).
6. `gps_long(abs) ∈ [778000, 779200]` (scaled by 10,000).
7. `valid` = AND-chain of checks 2–6 (degree-2 product chain).
8. **`valid_claim === valid`** — the claim must match reality; proving a
   `valid_claim = 1` with any violated rule makes **witness generation fail
   outright** (this is the v2→v3 fix; v2 allowed honestly proving `valid=0`).

**What the circuit does NOT constrain:** the file bytes themselves (only the
hash limbs the *prover supplied*), the detector verdict, and the truthfulness
of the metadata. The file↔hash loop is closed *outside* the circuit by the
verifier's SHA-256 recompute.

## 3. What the verifier checks, in order (`scripts/verify_media.js`)

Fail-closed at every step; each check is printed. Exit 0 = ACCEPT:

1. Audio file exists and has extension `.wav`/`.flac`.
2. `proof.json` and `public.json` parse as JSON; `public.json` is an array.
3. Trusted vkey is loaded from the repo path `outputs/v3/verification_key_v3.json`
   and its SHA-256 must equal the hard-coded pin `cbae94c0…6e93c` (override
   requires an explicit `--expect-vkey-sha256`; a key bundled with the proof
   is never trusted). `nPublic` cross-checked against the public array length.
4. Public signals: exactly 4 decimal strings in order
   `[valid, media_hash_hi, media_hash_lo, valid_claim]`.
5. **`valid == "1"` AND `valid_claim == "1"`** (claim gate).
6. SHA-256 of the supplied audio file is recomputed **by the verifier**; both
   128-bit limbs must equal the proof's public limbs.
7. Actual `snarkjs.groth16.verify(trustedVkey, publicSignals, proof)` via the
   local library; accept only a literal `true` (false/exception/anything else
   ⇒ REJECT).

**Final decision:** print `RESULT : ACCEPT` + exit 0, or `RESULT : REJECT` +
exit 1 (usage error = exit 2). Acceptance means precisely: *the supplied file's
SHA-256 matches the limbs of a proof that verifies under the trusted key with
`valid = valid_claim = "1"`* — **not** "authentic audio".

**`verify_fully.js` adds (after Part A = the above, in a fresh process):**
record JSON parses → `record_version == 1` → `record_type == simulated_capture_record`
→ required fields present → issuer public key from trusted path
`%USERPROFILE%\zkp-demo-issuer-keys\issuer_public.pem` whose SHA-256 matches
the hard-coded pin `38fefd71…ddf645` (any `--trusted-pubkey` override demands
an explicit `--expect-pubkey-sha256`) → canonical field string rebuilt and its
SHA-256 equals `canonical_sha256` (altered-field detection) → Ed25519
`crypto.verify` under the pinned key → `record.file_sha256` equals the audio's
SHA-256 → `record.vkey_sha256` equals the trusted vkey's SHA-256.
Output: `RESULT : FULL-VERIFY ACCEPT` (exit 0) or `FULL-VERIFY REJECT — <reason>`
(exit 1) with distinct failure messages for altered fields vs wrong key.
